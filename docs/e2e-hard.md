# 硬问题集：答案横跨同一小节的两个事实

- 时间：2026-11-19
- 动机：`docs/e2e-agent-eval.md` 的 12 道题**全被答对**（天花板效应），无法区分策略。这一组专测"分节切分能防止的那类失败"：答案需要**同一小节内相距很远**的两个事实，512 字符的定长块装不下。

## 1. 题目是怎么来的，以及它为什么是"故意加压"

8 道题由独立子代理针对 8 个指定小节各出 1 题，每题标出 `early_phrase` 与 `late_phrase`——两个必须在答案里同时出现的事实。

脚本对题目做**机械校验**，任何一条不过就退出：

- 两个短语都必须在该小节正文里**逐字存在**；
- 两者相距 ≥ 400 字符。

校验通过（实测距离 **727–3,664 字符**），远超 512 字符块能覆盖的范围。

> 这一组是**压力测试**，不代表一般查询的分布。它的价值在于把"分节 vs 定长切分"的结构差异变成可测量量，而不是造一个对自己有利的平均分。

## 2. 机械度量：双事实覆盖率（不经过任何 LLM）

这是本文件最硬的一条：给定检索到的上下文，它到底有没有同时包含两个关键事实？纯字符串匹配，可复跑、无判分员主观性。

| 策略 | 检索上下文同时含两个事实 |
| --- | --- |
| `docmunch`（按标题分节，top-5） | **8/8** |
| `recursive`（512 字符 + 80 重叠，top-5） | **2/8** |
| `full`（整篇语料） | 8/8 |

上下文成本：`docmunch` 16,722 token、`recursive` 11,147 token、`full` 91,745 token。

**怎么读**：

- 定长切块在 6/8 的题上**根本拿不到第二个事实**——不是"答得糙"，是证据不在上下文里。这是切分方式的直接后果，与模型能力无关。
- `full` 覆盖率当然 8/8，但代价是 91,745 token：语料已经大到"整篇塞入"在实际会话里不可行（这一轮因此**没有**跑 `full` 的 LLM 作答，见下）。
- `docmunch` 用 1.5 倍于定长块的上下文，换来 4 倍的覆盖。

## 3. LLM 作答结果

三种策略各由一个独立子代理作答（只允许读自己的上下文文件，禁止读仓库），再由独立子代理对匿名 A/B/C 列判分。

三种策略各由一个独立子代理作答（只允许读自己的上下文文件，禁止读仓库），再由独立子代理对匿名 A/B/C 列判分。

```
questions: 8

strategy      correct   partial   wrong    score   ctx tokens  per-question
---------------------------------------------------------------------------
none                0         0       8    0.000          624            78
recursive           4         4       0    0.750        11147          1393
docmunch            8         0       0    1.000        16722          2090
```

- `none` 全组"无法确定"，控制组再次成立；
- `recursive` 4 题全对、4 题只答对一个事实（`partial`）——与机械度量吻合：它在 6/8 的题上拿不到第二个事实，其中多数连"答不全"都只能勉强作答；
- `docmunch` 8 题全对。

**成本对照**：docmunch 用 16,722 token（每题 2,090）达到 1.000；recursive 用 11,147 token（每题 1,393）得到 0.750。即**多花 50% 上下文，换 0.250 的准确率**。`full` 未跑（91,745 token 超出作答预算）。

**必须说清的限定**：这一组题是**为探测这个失败模式而构造的**，所以分节方案占优是设计使然，不能反推"docmunch 普遍更准"。若换成单点事实题（第一轮 12 题），三者全部满分、毫无区别。真实查询里"横跨小节"的比例未知，本实验没有测这个比例。

## 4. 结论

1. **在"答案横跨小节"这类问题上，分节检索的证据覆盖率是定长切分的 4 倍（8/8 对 2/8）**，这是机制差异，不是模型差异。
2. 这解释了为什么第一轮 12 道单点事实题全都答对：那些题任意策略都能拿到证据，看不出差别。**评测若只出单点事实题，等于没测到分节的价值。**
3. `full` 的覆盖率与 `docmunch` 相同，但上下文是 5.5 倍（91,745 vs 16,722 token）——这仍不是"我们更准"，而是"同等覆盖下更省"。

## 5. 这类"横跨小节"的问题在语料里有多常见

上一节说了难题集是**构造**的，那自然要问：这种形状在真实语料里占多少？没有人手上有本项目的真实查询日志，所以测不了"问题分布"。能诚实测的是**结构那一半**：一个小节有多长，一个 512 字符块能覆盖多少（`tools/section_shape.py`）。

```
corpus: 27 docs, 359 sections        (docs/ 的快照，随文档增加而漂移)

section length (chars)            313 median /      807 p90 /    3990 max
section length (tokens)           206 median /     2024 max

sections longer than one 512-char chunk : 96/359  (27%)
sections longer than two chunks            : 21/359  (6%)
mean chunks needed to cover a section      : 1.35

labelled questions whose gold section needs >1 chunk: 6/18  (33%)
```

> 分母是 `docs/` 的当前快照，所以比例会随本项目继续写文档而小幅漂移（实测 26%→27%）。CI 每次 push 都重跑这个脚本，数字以 CI 输出为准；这里给的是量级而不是常数。

**怎么读**：

- **26% 的小节超过一个 512 字符块**，平均一个小节需要 1.35 个块才能覆盖完整。也就是说，只要问题落在小节的后半部分，单块检索就注定拿不到它。
- 在我们标注过的 18 个问题上，**33%（6/18）的金标小节需要多个块**。
- 这不是说 26–33% 的真实查询都会失败——那需要查询日志才能说。但它说明这个失败模式的**分母不是边角料**：至少四分之一的内容在结构上就放不进一个块。

**仍然不能主张**：真实用户问题的分布。本文件能说的是"结构上四分之一的节装不进一个块"，不能说的是"四分之一的提问会踩中"。

## 6. 局限（说清楚才可信）

| 局限 | 说明 |
| --- | --- |
| 题目是构造的 | 8 道题专为"横跨小节"设计，不代表真实查询分布；真实查询里这类比例未知 |
| 样本极小 | 8 题、8 个小节、单次运行 |
| 覆盖 ≠ 答对 | 证据在上下文里，模型仍可能读漏；第 3 节就是检验这一点 |
| 语料是本项目文档 | 领域集中；换语料结论可能变化 |
| `full` 未做 LLM 作答 | 91,745 token 超出作答代理的实用预算；这本身就是"整篇塞入不可行"的证据，但意味着 `full` 的准确率缺失 |

## 7. 复跑

```sh
moon build --target native
pip install langchain-text-splitters rank-bm25 tiktoken

python tools/e2e_hard_prepare.py          # 校验题目 + 生成 3 份上下文包 + 机械覆盖率
# 3 个作答代理（各自只读自己那份上下文包）→ _e2e/answers/hard_<strategy>.json
python tools/e2e_blind.py --tag hard
# 独立判分代理 → _e2e/blind/hard_verdicts.json
python tools/e2e_score.py --tag hard
python tools/section_shape.py         # 第 6 节：小节长度分布
```

题目文件 `_e2e/hard_questions.json` 由独立代理生成，`early_phrase` / `late_phrase` 与距离可在 `e2e_hard_prepare.py` 的校验输出里逐条核对。
