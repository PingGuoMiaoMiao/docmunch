# 检索证据：召回、上下文完整性与成本收益

- 时间：2026-11-18
- 触发：初审驳回意见要求「针对真实代理任务中的召回、上下文完整性与成本收益进行清晰说明并附带对照案例」
- 复跑：`python tools/retrieval_eval.py`、`python tools/cost_model.py`
- 结论先说：**之前写的「取回 O(1)」是错的**，已按实测改写；节级检索的收益在「上下文 token」与「读取放大率」，不在「常数时间」。

---

## 1. 三个对照系统

| 系统 | 做什么 | 对应现实中的做法 |
| --- | --- | --- |
| `full` | 不检索，把全部文档塞进上下文 | 「文档不大就整篇贴进去」 |
| `chunk` | 定长 512 字符 + 80 字符重叠切块，块级 BM25 | LangChain / LlamaIndex 的 `RecursiveCharacterTextSplitter` + 检索 |
| `section` | docmunch：标题对齐分节（字节偏移 + sha256），节级 BM25 | 本项目 |

语料：本仓库 `docs/`，**20 份文档 / 286 节 / 250 个定长块**。
问题集：**18 个真实问题**（中英混合），每个问题标注「金标文档 + 金标小节标题 + 必须在上下文里出现的短语」。问题与标注在 `tools/retrieval_eval.py` 的 `GOLD` 里，可逐条核对。

## 2. 结果

```
corpus: 20 docs, 286 sections, 250 chunks; k=5

system          hit@1      hit@5   complete  avg ctx tokens
------------------------------------------------------------
section         8/18       17/18       17/18             1853
chunk           9/18       13/18       12/18             1328
full           18/18       18/18       18/18            52755
```

三个指标的定义：

- **hit@k**：返回的前 k 个结果里，是否有内容同时属于金标文档、且包含标注短语；
- **complete**：金标小节是否**整节**进入上下文（不是被切块边界切掉一半）；
- **ctx tokens**：交给模型的上下文估算 token 数（ASCII 约 4 字符/token，CJK 约 1 字符/token）。

### 怎么读这张表

1. **`full` 召回必然 100%，但它不是"更好"，而是"不可能长期用"**：每次都把 5.3 万 token 塞进上下文，是节级方案的 **28 倍**。语料再大一倍，它就超出任何模型的上下文窗口。
2. **`chunk` 的 hit@1（9/18）略高于 `section`（8/18），但 hit@5 掉到 13/18，完整性只有 12/18**。这是定长切分的结构性缺陷：切块边界不认识标题，把「标题在上一块、正文在下一块」拆开，检索到了正文也拿不到它的标题归属，反过来也一样。
3. **`section` 用 1.4 倍于 chunk 的上下文，换到 hit@5 94% / 完整 94%**；相比 full 省掉 96.5% 的上下文。

**我们不掩饰的部分**：hit@1 上节级并没有赢（8 vs 9），因为问题措辞与目标节的用词不一定重合；节级方案的收益在「多给几个候选时能不能覆盖到」以及「覆盖到的时候是否完整」，而不是「第一个就对」。真实 Agent 通常取 top-3~5 再让模型挑，所以 hit@5 更贴近实际使用。

## 3. 成本：实测的取回代价

`python tools/cost_model.py`，同一台机器、CLI 冷进程、7 次取中位数。

| 文档数 | 节数 | index.json | 进程启动 | search | fetch 单节 |
| --- | --- | --- | --- | --- | --- |
| 20 | 286 | 437.5 KB | 20.0 ms | 40.8 ms | 30.4 ms |
| 100 | 1430 | 2187.1 KB | 26.6 ms | 126.0 ms | 74.4 ms |
| 400 | 5720 | 8773.4 KB | 25.9 ms | 443.8 ms | 242.3 ms |

扣掉进程启动后的操作成本：

```
  286 sections: search 20.7 ms, fetch 10.3 ms
 1430 sections: search 99.4 ms, fetch 47.9 ms
 5720 sections: search 417.8 ms, fetch 216.4 ms
```

**斜率约 0.073 ms / 节，与实际取回多少字节无关。**

也就是说，真实成本模型是：

```
单次取回 ≈ 加载并解析索引 O(节数)  +  线性定位 O(节数)  +  读该节字节区间 O(节字节)
```

**所以「O(1)」是错误表述，正确表述是：**

> 取回的**磁盘 IO** 与文档大小无关，只与该节大小有关（实测读放大率 **2%**：528 KB 文档里取一节 10.8 KB）；
> 但每次调用仍要加载并扫描元数据索引，**开销与节数近似线性**（约 0.073 ms/节）。

大文档对照：

```
single 528 KB document, 50 sections:
  fetch one section (10820 B): 24.0 ms
  section size / document size: 0.0200
```

这正是节级方案相对「整篇读取」的实质收益：**读放大率 2%**，而不是宣称的常数时间。

## 4. 已知短板（不打算靠措辞掩盖）

| 短板 | 现状 | 影响 |
| --- | --- | --- |
| 每次调用都重新加载索引 | CLI 冷进程 0.073 ms/节 | 5720 节时单次取回 216 ms，交互式场景偏慢 |
| 长驻 MCP 进程未做索引缓存 | 当前每请求同样加载 | 加内存缓存可把每请求成本降到「扫描 + read_at」；**未实现** |
| 索引是单个 JSON | 5720 节 8.8 MB | 上万节需要分片或二进制定长记录 |
| 只有 18 条问题 | 自我评测，非第三方标注 | 存在选择偏差；欢迎用别的语料复跑 |
